# Final analysis — LLM-generated enemy behaviour in Cosmic Animosity

Module: DS 340W research project. Engine: Unreal Engine 5.7.4 (Blueprint-only, no C++ module).
Project: Cosmic Animosity. Level: `/Game/Research/Maps/Lvl_Research_Trial`.

This document consolidates both evaluation sets, compares the automated validator's
classifications against measured gameplay, attributes every observed problem to the layer that
produced it, and states what the experiments support and what they do not. All numbers here are
derived from the consolidated CSVs in `results/analysis/`, which are themselves derived from the
preserved measurement files — nothing in this document is hand-entered.

Companion documents, not superseded: `docs/methodology.md` (design and research questions),
`docs/evaluation_metrics.md` (metric definitions — see §7.5 for the one place where it and the
delivered harness disagree), `docs/IMPLEMENTATION_LOG.md` (per-candidate translation record,
including §18 Phase 7H), `docs/BASELINE_COMPARISON.md` (per-candidate measurement records,
including the §16.5 correction block), `docs/RESEARCH_PROGRESS.md` (running project state).

## 2. Evaluation Set 1 — automated validation of the 40 outputs

### 2.1 Headline counts

| Layer | Metric | Result |
|---|---|---|
| M1 JSON validity | `json.loads` on verbatim text | **40 / 40 (100 %)** |
| M2 Structural validity | keys, types, node ids, depth, children count, parameter ranges | **26 / 40 (65 %)** |
| M3 Action validity | every action in the 4-action space | **40 / 40 (100 %)** |
| M4 Logical correctness | deterministic rules over the JSON only | **12 VALID / 14 REVIEW / 14 INVALID** |
| M5 Correction class | modification needed to reach a clean status | **none 12 / mapping 14 / logic 14** |

M2's 14 failures are exactly the 14 INVALID rows: 10 of them fail on children count (`S1`,
a single-child composite) and 4 fail only on a parameter range (`S5`, `retreat_distance_cm`

M4 and M5 are properties of the emitted JSON, not of a tree in an engine. `VALID` therefore means
*passed every automated check*, and this document never uses it as a synonym for *implementable*;
§9.1 gives the measured evidence for why that distinction matters.

### 2.3 Which findings actually occur

Rows carrying each code across the 40 outputs:

| Code | Type | Rows | Meaning |
|---|---|---|---|
| `L5` | ambiguous → review | 18 (12 review-only + 6 alongside a structural fail) | attack not guarded by any `distance_to_target` condition on its path |
| `S1` | structural fail | 10 | composite with one child |
| `S3` | advisory | 10 | redundant single-child wrapper (same rows as `S1`) |
| `S5` | parameter fail | 6 | `retreat_distance_cm <= attack_range_cm` |
| `L8` | advisory | 4 | attack threshold differs from `attack_range_cm` by > 200 cm |
| `L3` | ambiguous → review | 2 | duplicate sibling conditions, shadowing risk only |

`L5` is the only code whose row count exceeds the number of rows whose status it determines. It is an
*advisory* finding: it promotes a row to `REVIEW` when it is the sole finding (12 rows), and rides
along as an additional note when a deterministic structural defect has already made the row `INVALID`
(6 rows). `S3` and `L8` behave the same way in the opposite direction — they never change a status at
all. §6.3 reconciles the 18 against the 12 `L5` review entries in full.

`L1` (no action at all) and `L2` (provable contradiction) occur **zero** times. Under the
project's unreachability policy — a selector continues when a child fails, so overlapping siblings
are never scored as unreachable — that is the intended result: no output was rejected for a
logical contradiction, only for shape and for parameter agreement.

### 3.3 Attack-range compliance (recorded as `reaction_correctness`)

The rule reported under this heading is **attack-range compliance**: one uniform test, applied
identically to all twelve rows:

> **pass iff zero damage events were recorded beyond `attack_range_cm + 50 cm`.**

Three definitional points, because the harness column this is read from is named
`reaction_correctness` in `results/gameplay/*_summary.csv`:

1. **The label is narrower than the name suggests.** The test sees only the *distance at which damage
   was delivered*, compared against the tree's own authored band. It does not see whether the correct
   action was chosen for the situation, whether branches fired in the intended order, or whether the
   tree satisfied the specification it was generated from. A tree that never fires passes vacuously,
   so the rule can never fail a tree that declines to engage.
2. **It is not `docs/evaluation_metrics.md`'s Set 2 behaviour-correctness metric.** That metric pairs
   a `TRIGGER` with an `ACTION_START` inside a tolerance and would need the trial-id / event-id
   instrumentation described in §7.5, which was never built. No number in this document measures it,
   and no "behaviour correctness rate" is reported.
3. **The recorded verdicts are unchanged.** The per-row `pass` / `fail` values below are exactly what
   the runs produced, reproduced from the preserved summary files. Only the *label* has been narrowed.
   `set2_candidate_gameplay.csv` carries them as `gen_range_compliance` / `base_range_compliance`
   alongside the source column name, so the mapping back to the preserved files is explicit.

| # | Generated | Baseline | Interpretation |
|---|---|---|---|
| 1 | pass | fail | generated never exceeded 218.6 cm; baseline fired at up to 1421.2 cm |
| 2 | pass | fail | generated dealt no damage at all — a vacuous pass |
| 3 | pass | **pass** | the only row where the baseline came inside the band too (0 events over 1500 cm) |
| 6 | pass | fail | vacuous pass |
| 5 | pass | fail | vacuous pass |
| 4 | pass | fail | generated never exceeded 209.3 cm; baseline fired at up to 1275.6 cm |

Two things must be read into this table:

1. **Every baseline `fail` is a metric-definition artefact, not baseline drift.** The threshold is
   the candidate's authored range; the baseline has no authored range and shoots on sight. The
   figure quantifies how undisciplined the control is relative to each candidate's own policy. It
   is not a quality score for `BP_AICharacter`.
2. **A vacuous pass is not a positive result.** **Three** of the six generated `pass` verdicts were
   achieved by not shooting (#2, #6, #5). Range compliance and damage delivered are separate axes,
   and §4 identifies a different reason in each case. The other three (#1, #3, #4) passed while
   dealing damage, which is the only combination this rule treats as evidence that a band was
   actually held.

**Correction to a published verdict.** `docs/RESEARCH_PROGRESS.md` §12.2 records candidate #1's
pair as "pass / pass" while also recording 11 baseline events beyond its 350 cm ceiling — a
contradiction. Under the uniform rule applied to every other row the pair is **gen pass / base
fail**. This analysis uses the uniform rule; the per-phase numbers themselves are unchanged.

## 4. Action reachability

Reachability was measured per branch, and **the instrument that revealed it differed every time**.
No single metric — movement, task lines, `weapon_fired`, or refusal counts — found all of them.

| | #1 | #2 | #3 | #6 | #5 | #4 |
|---|---|---|---|---|---|---|
| `move_to_target` | reached (9 SUCCESS / 0 FAIL) | reached (6 / 0) | reached (6 / 1) | not in tree | reached (21 / 1) | reached (9 / 0) |
| `move_away_from_target` | not in tree | reached (1 SUCCESS, sawtooth) | entered, never succeeds (24 FAIL / 0 SUCCESS) | never executes (1 FAIL / 0 SUCCESS) | reached (11 / 22) | not in tree |
| `attack` | reached (36 events, 0 refusals) | **unreachable** (0 lines, 0 damage) | reached (35 events, 0 refusals) | **entered, always refused** (106 / 106) | **entered, always refused** (1 / 1) | reached (55 events, 10 refusals) |
| `wait` | not observable | selector satisfied | not observable | not observable | not observable | not observable |

Figure: `results/analysis/figures/fig3_action_reachability.svg`. Per-action evidence strings are in
`action_reachability.csv`.

Three points that matter for the discussion:

- **`BTTask_Wait` prints nothing.** Sequence position is not measurement. Every "selector
  satisfied" or "not observable" cell is a stated limit, not a finding.
- **"Entered, always refused" is a different failure from "unreachable", and they have different
  causes.** #2's attack node never ran; #6's ran 106 times and was refused 106 times by its own
  in-task range gate. Both produced zero damage. Collapsing them into one "attack failed" category
  would hide the mechanism.
- **#5's `attack` cell is an implementation observation, not a generated-logic one** — see §5.2.
  Its graph-identical rebuild attacks in the same session.
- **Candidate #1's refusal count was recovered from the preserved editor log**, which is the only
  reason its `attack` row carries a count at all (evidence gap G2). In `Saved/Logs/Cosmic_Animossity.log`
  over the Phase 7B window 01:02:40–01:03:54, `BTTask_EnemyAttack: out of range - FAILURE` occurs **0**
  times and `BTTask_EnemyMoveToTarget: SUCCESS` occurs **9** times, with every other task prefix at 0.
  So candidate #1's attack gate never refused a shot in three trials: it fired 36 times, all inside its
  band, and never had to refuse.

### 5.1 The four-way distinction, stated once

| Layer | Signature | Examples from this study |
|---|---|---|
| **Generated logic** | The authored structure or parameter makes an intended action impossible or self-cancelling, independent of the engine. | #2's attack sits behind a `d > 800` the preceding approach task undoes on arrival; #6's `d >= 900` gate against an `AttackRange` of 900 is a zero-width window; #3's generated `retreat_distance_cm` of 2000 exceeds what the arena can deliver. |
| **Engine / task behaviour** | A Blueprint task's own precondition, success band or abort mode changes what the authored gate means. | `BTTask_EnemyMoveAwayFromTarget` has an entry precondition (`d < RetreatDistance`) and a 150 cm success band; `FlowAbortMode = Self` ends #6's retreat 250 cm before that band; the implementation-chosen `AcceptanceRadius = attack_range_cm - 150` interacts with #2's approach. |
| **Environment / navigation** | The arena's navmesh extent or `MoveToLocation` projection, not the AI, sets the reachable set. | `ProjectDestinationToNavigation = false` plus `AllowPartialPath = true` turns an off-navmesh retreat goal into a partial path ending at the navmesh edge (y ≈ 1433), which is the 834–835 cm plateau; the navmesh extent (~1976 cm) is what makes #3's 2000 cm retreat impossible. |
| **Instrumentation** | The measurement cannot see the thing being claimed. | 2.9 Hz sampling cannot resolve a 0.1 s blackboard staircase; `BTTask_Wait` emits nothing; `OperationType` is not readable from Python, so the contents of #5's compiled data cannot be inspected. |

Two rules follow, and both were violated at some point in this project before being corrected:

- **Task success is not proof of correct behaviour.** #5's retreat task logged 11 `SUCCESS` lines while the tree never fired; #2's approach logged 6 successes while the attack branch never ran. A "behaviour failure rate" built from task outcomes alone would have scored both trees as working.
- **A clean rule set is not proof of a working tree.** §6 shows this quantitatively.

### 5.2 Candidate #5 — reclassified as a compiled-asset discrepancy

This replaces the `priority-starvation` explanation published at the end of Phase 7F.

**What still stands, unchanged.** The asset at `/Game/Research/AI/BT_Behavior_P03_G02` retreats
834–835 cm at far range, never puts a projectile in the air, and deals 0 damage in three comparison
trials against a 330.0 baseline. The 66 baseline damage events it was measured
against, its 11 retreat `SUCCESS` lines and its single in-task attack refusal at ≈1500 cm are all as
recorded. `P03CMP_*` was not re-run and must
not be.

**What is withdrawn.** The claim that the attack was starved by priority — that two sequences
ending in unguarded `Wait`s satisfied the selector ahead of it. Phase 7H built
`BT_Behavior_P03_G02_R1`, a node-for-node rebuild of the same tree, and dumped both:

- **14 nodes, 0 differences** across role, class, node name, parent index and every property value,
  including the `Less / 800.0` and `Greater / 1200.0` decorators and `CanAttack Equal`.
- Blackboards equal. `.uasset` sizes 19 782 vs 19 884 bytes.
- In the same session, in an order-controlled **A/B/A** sequence (`R1 → ORIG → R1B`), the rebuild
  closed **617.9 / 618.2 cm toward the player and attacked for 15–25 damage in every phase**, while
  the original retreated **834.5 / 835.1 cm away and dealt 0**.

Figure: `results/analysis/figures/fig7_rebuild_vs_asbuilt.svg`. Diagnostic rows, kept separate from
candidate measurements, are in `phase7h_rebuild_diagnostics.csv`.

**Conclusion — established at the asset level.** The authored tree is not priority-starved. Two
assets with byte-identical authored structure — the same 14 nodes, the same property values, the same
blackboard — behaved in opposite directions in the same session: one closed on the player and attacked
for 15–25 damage per phase, the other retreated and never fired. Because the graph read-back of both
is identical, the difference cannot lie in authored logic. It lies in what each asset compiles to, and
it is established at that level: **the two assets differ.**

**What is still unresolved — the internal mechanism.** Which compiled field carries the difference,
and what produced it, is not identified. `OperationType` (the byte `BTDecorator_Blackboard` actually
compares) is not exposed by `AuraBehaviorTreeStatics`, and `UBehaviorTree::RootNode` is protected, so
there is no supported runtime walk. The correct reading is therefore: **an asset-level divergence,
established; its internal mechanism, unidentified.** No specific field, byte or cause is claimed here,
and none should be inferred from the behavioural difference alone. Candidate #5's gameplay numbers
must therefore be labelled an **implementation discrepancy**, and they must not be counted as a
generated-logic failure in any rate computed from this study.

**What the reclassification does *not* excuse.** Two findings attached to #5 survive on their own
evidence: its `L5` (no distance condition on the attack path) is a genuine property of the generated
specification, and that risk was never exercised (F09) — `n8` ran once, at ≈1500 cm, and was
refused. So #5 remains the only measured tree of the six whose authored policy was neither
confirmed nor refuted by gameplay.

**What Phase 7H established about decorators in general** — needed so this reclassification is not
read as "decorators are unreliable":

1. `BrainComponent.is_running()` returned 1 in 41 of 41 diagnostic samples while the pawn never
   moved: "tree running" and "pawn moving" are separate observables, so earlier zero-displacement
   results were not a dead tree.
2. A leaf guarded by `DistanceToTarget < 250` entered its task **12 times in 8 s at 200 cm and 0
   times at 600 cm**; candidate #6's preserved data, guarded by `< 900`, moved 0.0 cm in both
   1500 cm phases and 617.9 / 951.4 cm at 600 / 200 cm. Numeric comparisons are honoured.
3. A decorator **can** admit one entry on a stale key: the guard control entered exactly once at
   `far_1500_again`, printing `already beyond retreat range d=1500.02`, because `DistanceToTarget`
   is a 0.1 s staircase still carrying the previous phase's 200 cm. The probe samples at 3 Hz and
   cannot resolve that window.

So the defect is a property of one artifact, not of the decorator mechanism.

| 4 | REVIEW | `L3` | **275.0** | best result in the set; the flagged redundancy was harmless |

### 6.2 What the classification does not measure

M1–M5 check syntax, shape, the action vocabulary, parameter ranges and a fixed rule set. They do
not score, and by construction cannot score:

- **sibling order** — #2 fails only because of the order of the children inside one sequence;
- **agreement between a decorator threshold and the task parameter it gates** — #6's `d >= 900`
  against `AttackRange` 900;
- **reachability under a task's own precondition and success band** — #3's retreat, #6's retreat;
- **feasibility in the arena** — #3's 2000 cm retreat against a ~1976 cm navmesh;
- **fidelity of the compiled artifact** — #5's divergence, which no validator reading JSON could
  ever see.

That is the honest boundary of automated behaviour-tree validation as exercised here: the
validator scores the *specification*, and all three zero-damage outcomes happened in the gap
between the specification and the running tree.

### 6.3 The direction of the `L5` result

`L5` is the corpus's largest ambiguity category — **18 of 40 rows carry the code** — and its recorded
prediction is that an unguarded attack "may fire far out of intended range". Three counts must not be
confused here:

| Count | Meaning |
|---|---|
| **18** | rows whose `finding_codes` contain `L5`, in any combination |
| **12** | rows whose status is `REVIEW` and whose only finding is `L5` — the review queue |
| **6** | rows carrying `L5` **alongside** a deterministic structural defect (`S1` and/or `S5`); their status is `INVALID` and `L5` rides along as an additional finding |

That overlap is the whole explanation of the 18-versus-12 gap, and it is a property of the code
rather than an inconsistency in the data: `L5` never makes a row `INVALID` on its own, and it does not
suppress a row's other findings. The six rows in both tallies are `P09-G01` (in both rounds) plus
`P08-G01`, `P09-G02`, `P09-G03` and `P10-G03` — five of them `L5;S1;S3`, and `P08-G01`
`L5;L8;S1;S3;S5`. The 14 `REVIEW` rows split as 12 x `L5` + 2 x `L3`, and it is the 12 that §6.4
counts as unbuilt.

In the one `L5` tree that was built (#5), the attack never fired at all. That is one observation, and
after §5.2 it is partly an implementation artefact rather than a statement about generated logic. The
measured-set evidence therefore does **not** establish whether `L5` failures fail open (out-of-range
shooting) or closed (no shooting); 17 of the 18 `L5` rows were never built.

### 6.4 Non-generalisability, stated explicitly

- Six of 40 outputs were measured, and they were **selected purposively**, not sampled randomly.
  No percentage computed over these six is an estimate of a rate over the 40.
- **14 INVALID outputs were never built** (10 carry `S1`, 6 carry `S5`, 2 carry both). Nothing in
  this document is a claim about their gameplay.
- **12 of the 14 REVIEW outputs were never built** (11 x `L5`, 1 x `L3`). The `L5` category, which
  is the largest single finding in the corpus, has one measured member.
- The correct statement is about **existence and mechanism**: rule-clean trees can be behaviourally
  inert, and the mechanisms that made them inert are identifiable. It is not a statement about
  prevalence.

## 7. Metric reliability and the sampling rates

### 7.1 What was measured, and how fast

There is no in-engine `TRIALDATA` event stream in this project. Every Set 2 number comes from
Python sampling a live PIE world, and the sampling rate differs by a factor of twenty between
phases:

| Candidate | Subject | Samples/s | Interval | First-damage resolution |
|---|---|---|---|---|
| 1 | generated / baseline | 2.92 / 2.93 | 0.343 / 0.341 s | ±0.34 s |
| 2 | generated / baseline | 2.91 / 2.93 | 0.344 / 0.341 s | ±0.34 s |
| 3 | generated / baseline | 2.89 / 2.92 | 0.346 / 0.342 s | ±0.35 s |
| 6 | generated / baseline | 2.93 / 2.92 | 0.341 / 0.342 s | ±0.34 s |
| 5 | generated / baseline | 2.91 / 2.91 | 0.344 / 0.344 s | ±0.34 s |
| **4** | generated / baseline | **59.48 / 58.65** | 0.017 s | **±0.017 s** |

The 2.89–2.93 Hz band is PIE running background-throttled; candidate #4's phase ran unthrottled.

### 7.2 Which comparisons are reliable at both rates

- **Damage totals and event counts are exact at both rates.** Verified in all twelve rows:
  `damage_total = damage_events x 5.00` to the last digit, because damage is accumulated from
  player-health deltas rather than from sampled instant values. The weapon cadence is 1.0 s, which
  exceeds even the coarsest 0.346 s interval, so no event can hide between samples.
- **Within-session latency comparisons are valid at 2.9 Hz** — both subjects in a row are sampled
  by the same instrument at the same rate.
- **Cross-rate latency comparisons are invalid.** Candidate #4's latencies cannot be compared with
  the other five; its 0.017 s resolution is twenty times finer than theirs.

### 7.3 Which latency claims survive, and which do not

Figure: `results/analysis/figures/fig5_timing_resolution.svg`. The floor at 2.9 Hz is ±0.344 s.

| Claim | Magnitude | Supported? |
|---|---|---|
| #1 at `far_1500` is slower than baseline (4.195 vs 1.304 s) | 2.89 s | yes — 8x the floor |
| #4 is slower than its own baseline (1.991 vs 0.810 s) | 1.18 s | yes — same session, same rate |
| #3 is slower than its own baseline (2.161 vs 1.225 s) | 0.94 s | yes — 2.7x the floor |
| #1 at `close_200` differs from baseline (1.121 vs 1.222 s) | 0.10 s | **no** — inside the floor |
| Any latency difference between #4 and the other five | — | **no** — different instrument resolution |

Quoting the 0.10 s `close_200` difference as a real finding would be an instrument artefact. The
published record already says this (`docs/BASELINE_COMPARISON.md` §6.1); it is repeated here
because §3.2's latency column invites exactly that error.

### 7.4 Behaviour failures: what this metric can and cannot say

The six comparison phases do not share one behaviour-failure schema:

- candidate #1's file is a 4-column summary (`move_task_success`, `move_task_failure`,
  `failure_rate`, `source`) with 2 rows — one per subject;
- the other five are 11-row `task_line_prefix` tables counting each terminal task line separately.

The raw counts are preserved as recorded and normalised into `action_reachability.csv`. Three
definitional points hold throughout:

1. **A task line is not a behaviour.** `BTTask_EnemyMoveAwayFromTarget` prints on every terminal
   path (three failure reasons plus success); `BTTask_EnemyAttack` prints **only on refusal**. So a
   tree that never fired and a tree that fired successfully can both show zero attack lines. That
   asymmetry is why #6's 106 refusals and #2's 0 lines are different findings, not the same one.
2. **The baseline has no tree and executes no tasks**, so its failure count is `n/a`, never 0. A
   comparison of failure *rates* between the two subjects is meaningless.
3. **Task success is never reported as correctness.** The scored rule is the attack-range compliance
   test of §3.3, which is about distance at damage and nothing else; it is scored against each
   tree's own policy, never against the baseline. No metric in this study measures whether the tree
   chose the right action, which is the broader sense of reaction correctness.

### 7.5 A definition that was never reconciled

`docs/evaluation_metrics.md` defines Evaluation Set 2 from `TRIALDATA` log lines matched by `evt`
id, and it names `results/implementation_log.csv` as an output. **Neither exists.** The pipeline
that would emit them was never built; Set 2 was delivered by Python sampling instead. The
definitions in §7.2–7.4 above are the ones the measurements actually use. The original document is
preserved unedited as the design record, and this section is the reconciliation. Any "behaviour
correctness rate" or "reaction time" figure defined from `TRIGGER`/`ACTION_START` pairs must not be
reported for this project, because no such pair was ever recorded.

## 8. Threats to validity

1. **One model, one temperature.** `gpt-4.1` at 0.7 with one frozen prompt set. Nothing here
   generalises to LLMs generally.
2. **N = 40 with purposive selection for Set 2.** The 12/40 all-checks-passing rate carries roughly
   ±14 percentage points at 95 % confidence under a normal approximation, and the six measured trees
   are not a random sample of those 40. Percentages over six trees are descriptive only.
3. **Fourteen INVALID and twelve REVIEW trees were never built.** The most common finding category
   (`L5`, 18 rows) has one measured member.
4. **One arena.** Navmesh extent ≈1976 cm in y, one navmesh y-edge at ≈1433, a single combatant, a
   passive player and fixed spawns (enemy `(0, 600, 120)` yaw −90; player `(0, 600 − d, 98.2)`).
   Retreat distances above roughly 1976 cm are unachievable here regardless of the AI, and every
   claim about #3's close band is conditional on that.
5. **Sampling rate asymmetry.** §7.3. Latency is comparable within the 2.9 Hz group and within
   candidate #4, and not between them.
6. **Phase-start blackboard staleness.** `DistanceToTarget` is a 0.1 s staircase; a phase's first
   frame can read 0.0 or the previous phase's value, and a decorator can admit one entry on it.
   Measured once directly (`d=1500.02`) and invisible to 3 Hz sampling otherwise.
7. **Decorator versus in-task gate is not separable for #2 or #4.** Both members read the same key
   against the same threshold, so the run proves the pair refuses out-of-band shots, not which
   member refused on a given pass.
8. **Compiled-data contents are unreadable.** §5.2. The divergence is proven; the field is not.
9. **Some findings are measured but unexplained**: #4's trial-3 `far_1500_again` overshoot
   (1512.3 cm travelled, 546.0 cm end separation, 1 phase of 12); the consistent ≈1.1 s delay before
   #4's attack node is entered in out-of-band phases (9 of 9, but no measurement of the cause);
   trial-to-trial movement variance in #5's phases (0.0 / 833.2 / 820.0 cm at `mid_600` with
   identical setup).
10. **One disclosed cross-phase carry-over.** #4's single 250.1 cm event: `projectiles = 1` preceded
    it by 35 ms and the pawn had not moved. Counted in neither the pass nor the fail column.
11. **The Phase 7H A/B/A comparison is n = 3 runs of a rebuild pair**, not a three-trial set. It
    establishes the direction of the divergence, not a distribution.
12. **`retreat_health_pct` was never exercised anywhere.** No candidate tested health; #3's and
    #4's declared values are dead parameters, and the health-gated family (#2) was measured without
    the low-health stimulus in the comparison trials.

## 9. Results and discussion

### 9.1 RQ1 — generation reliability

> How reliably can an LLM produce behaviour specifications that are syntactically valid,
> structurally valid, expressible in the project's action space, and logically coherent?

| Layer | Result | Reading |
|---|---|---|
| Syntax | 40/40 | solved at this prompt set; no unparseable output |
| Action space | 40/40 | the 4-action vocabulary was never exceeded |
| Structure | 26/40 | 10 single-child composites, 4 parameter contradictions |
| Logic — passed every automated check | 12/40 (30 %) | 14 queued for review, 14 rejected |
| Correction needed | 28/40 | 14 mapping + 14 logic |

**What `VALID` does and does not mean.** M1–M5 are automated checks over the emitted JSON. A `VALID`
row passed all of them; that is the entire claim, and it is stated here as *12/40 passed every
automated check*, never as *12/40 were implementable*. The measured set is the evidence for the
distinction: **four of the twelve `VALID` outputs were built** (#1, #2, #3, #6), and they did not all
work — #2 and #6 dealt no damage at all, and #3 carried a retreat branch that can never succeed.
Nothing in this data supports the stronger reading, so none is made.

**Supported.** The failure surface is not syntax and not vocabulary behaviour — it is *shape and
parameter agreement*. Every rejection was either a structural rule (`S1`) or a numeric relationship
between two parameters (`S5`). **Zero** outputs were rejected for a provable contradiction (`L2`)
and **zero** for containing no action (`L1`). The model reliably produced something tree-shaped out
of the specified vocabulary; what it got wrong was arithmetic it had to infer — that a retreat
distance must exceed an attack range, and that a composite needs more than one child.

The prompt family dominates the outcome: P02 and P03 produced no INVALID
output in four attempts each, while P08 and P09 produced no VALID one. That is a prompt-design result
as much as a model result, and it is the strongest actionable finding for RQ1. The two fully rejected
families fail differently — P08 on the retreat-versus-attack-range contradiction in all four samples,
P09 on a single-child composite in all four — so "the worst prompt" is not one failure mode.

**Uncertain.** Whether the 30 % all-checks-passing rate is a property of this model, this prompt set,
or this schema cannot be separated by this design (§8.2). Implementability was never measured, so no
implementability rate is reported. Whether `L5` failures are dangerous (out-of-range shooting) or
benign (no shooting) is unresolved, because 17 of its 18 rows were never built — and the one that was turned out to be an implementation artefact (§5.2).

### 9.2 RQ2 — gameplay effectiveness

> When implemented in Unreal Engine, how do LLM-generated behaviours perform on shared combat
> metrics compared with the existing hand-built baseline enemy, and how well do they satisfy their
> own specification?

**Supported — the aggregate.** Across the six comparisons the generated trees dealt **630.0 damage
against the baseline's 2030.0, i.e. 31 %**. **Three of six dealt no damage at all (#2, #6, #5)**; the
other three (#1, #3, #4) dealt 53.7 %, 54.7 % and 71.4 % of their baselines respectively. Damage per
hit is identical (5.00) everywhere, so the whole gap is attack *uptime*, not damage per projectile.

**Supported — the one axis the generated trees win.** Attack-range compliance, the narrow rule of
§3.3. Generated trees produced **1 over-threshold event out of 126** (0.8 %) and **0 beyond the 50 cm
ceiling**; the baselines
produced **43 of 406** (10.6 %) and 40 beyond the ceiling. Restricting the claim to the three trees
that actually fired, the ratio is 1 of 126 against 43 of 406 — an order of magnitude. The generated
policy does what the brief asked: it holds fire until the target is inside the authored band.

**Supported — the cost.** Throughput and latency. The best generated tree reached 71.4 % of
baseline damage and was 2.5x slower to first contact (1.991 s vs 0.810 s, same session, same
59 Hz instrument). Candidate #1 was 54 % overall and 2.89 s slower at 1500 cm. The gap narrows at
close range and widens with distance — a policy effect, not a competence effect: the trees spend
the first seconds of every phase closing.

**Supported — the failure mechanisms, and that they are not the validator's.** Every zero-damage
outcome traced to one of three mechanisms, none of which M1–M5 scores: a branch unreachable because
of sibling order (#2), a gate disagreeing with the task parameter it guards (#6), or an as-built
asset that diverges from a node-for-node rebuild of its identical authored graph (#5, §5.2). Two of
the three are generated-logic failures; the third is not, and is reported only as an asset-level
discrepancy whose internal mechanism is unidentified. **`VALID` did not predict a working tree and
`REVIEW` did not predict a broken one** — the best measured result in the set came from an `L3` tree whose flagged redundancy was harmless, and
two rule-clean trees dealt nothing.

**Supported — reachability must be measured, per branch.** No single observable found all the dead
branches. Movement revealed #2's; task `SUCCESS`/`FAILURE` counts revealed #3's; `weapon_fired` and
`LastFireTime` revealed #5's; refusal-line counts revealed #6's and #4's. A study that measured only
damage would have reported three "failed" trees with no mechanism; a study that measured only
movement would have scored #5 as working.

**Uncertain.**

- **Prevalence.** Six purposively selected trees out of 40. "Three of six" is not "half of generated
  trees"; the correct statement is that rule-clean-but-inert trees exist and their mechanisms are
  identifiable (§6.4).
- **Whether the baseline comparison is a fair ceiling.** The baseline fires on sight with no range
  gate, so its damage advantage is partly the absence of a policy. Restricting both to the
  candidates' own bands would change the ratio, and the project's own metric-definition artefact
  (§3.3) shows how much that restriction moves the numbers.
- **Whether any of this transfers.** One arena, one navmesh extent, one combatant, three trials per
  subject, no opponent fire. The baseline's damage never dropped the player below 99 600 of 100 000
  health, so no trial reached a low-health condition and no defensive branch was ever legitimately
  triggered.
- **#5's true policy value.** Unresolvable with the preserved asset: the built artefact does not
  exercise its own tree, and the rebuild that does is a diagnostic instrument, not a candidate.
  #5's gameplay row should be cited as an implementation case study, never as evidence about
  generated logic.

### 9.3 The one-sentence conclusion per set

- **Set 1:** the model solved the format and the vocabulary but not the arithmetic — 12 of 40 outputs
  (30 %) passed every automated validation check, and every rejection was structural shape or a
  numeric contradiction between two parameters, never a malformed rule. Passing the checks is not
  the same claim as being implementable (§9.1).
- **Set 2:** automated validation classified the six trees and predicted none of their outcomes —
  rule-clean trees dealt no damage, the strongest performer was flagged for review, and every
  failure traced to reachability, to a gate disagreeing with the action it guards, or (once) to the
  compiled artifact rather than the authored logic.

### 10.2 Regenerating the deliverables

Both sets of artefacts are produced by saved, standard-library-only scripts, run from the project
root. Neither needs an editor session and neither reruns an experiment.

```
python scripts/build_analysis.py     # 1. rebuilds the 8 consolidated CSVs in results/analysis/
python scripts/make_figures.py       # 2. rebuilds the 7 SVGs in results/analysis/figures/
```

Order matters: `make_figures.py` reads the CSVs, so a data change must be followed by a re-run of it.

`build_analysis.py` reads the preserved sources and writes only into `results/analysis/`:

```
results/validation_combined.csv
results/gameplay/<prefix>_summary.csv
results/gameplay/<prefix>_phase_metrics_{generated,baseline}.csv
results/gameplay/G1*_phases.csv
```

with `<prefix>` in `{P7CMP, P02CMP, P04CMP, P07CMP, P03CMP, P01G2CMP}`.

**Six of the eight CSVs are derived** and reproduce from those inputs alone: `set1_validation_40.csv`,
`set1_family_status_matrix.csv`, `set2_candidate_gameplay.csv`, `set2_phase_metrics_all.csv`,
`metric_reliability.csv`, `phase7h_rebuild_diagnostics.csv`.

**Two are analyst-curated**, because they record judgements no source file contains, and are defined
as data tables inside `build_analysis.py` itself: `action_reachability.csv` (what each run established
about each branch) and `failure_attribution.csv` (which layer produced each finding). Their evidence
strings were transcribed from `results/gameplay/*_behavior_failures.csv` and the Phase 7C–7G
reachability records; the script does not re-read those files, so editing either table means editing
the script.

Every run prints a cross-check: per-candidate generated and baseline damage, the two totals, and the
zero-damage set. On the preserved data it must print `630.0 / 2030.0 (31.0 %)` and
`zero-damage candidates: [2, 6, 5] (3 of 6)`. That print is the regression test for the whole
derivation.

### 10.3 Re-running one candidate's comparison (only if a gap requires it)

1. Open `Lvl_Research_Trial`; PIE stopped.
2. Point `AIController_ResearchEnemy.BehaviorTreeAsset` at the candidate's tree and re-read the CDO
   to confirm. Never re-save a measured tree.
3. Run the phase's harness (`aura_<phase>_compare.start(...)`), wait, restore the arena.
4. Run the matching aggregator to write `_combined_phase_metrics`, `_combined_damage_events`,
   `_summary` and `_behavior_failures`.
5. Restore the controller to `BT_Behavior_P01_G02` and confirm by CDO read-back.
6. Nothing in `dataset/` is ever rewritten; `python -m unittest discover -s tests -v` must stay
   green before and after.

### 10.4 Standing constraints observed in this analysis

No original generated JSON, manifest, validation CSV, measured Behaviour Tree asset or existing
gameplay result was modified. No experiment was rerun. The Phase 7H instruments are labelled
instruments, never candidates. `BT_Behavior_P03_G02`'s divergent compiled data was preserved
because it is the finding. Generated logical weaknesses were not repaired. Task success was never
reported as proof of correct behaviour.
